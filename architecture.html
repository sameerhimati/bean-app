Bean — Architecture Reference

The architecture reference for Bean — the triage engine + the closed learning loop. Last updated 2026-06-25.

Historical design record

This page documents the 2026-06 engine, which has since been replaced.

The flat classify → assess → route() pipeline below (bean/routing.py, bean/loop.py, bean/prompts.py) was superseded first by the routing tree and then by the single-call notebook engine. Read it as the design record of that era, not as a description of current behavior.

What Bean is

Me Bean. Bean is a human-in-the-loop email triage and reply-drafting agent for a solo operator running ecommerce customer support on Proton Mail. Bean reads an incoming email, categorizes it into one of the operator's pre-defined fields, drafts a grounded reply from the matching template, and routes the result into one of three confidence buckets — HIGH (one-tap approve), LOW (needs a look), or FLAG (escalate, no draft). It never autosends.

The actual product

The thesis is calibrated uncertainty, not the drafting.

Matching email → category → template is the throwaway 80%. The product is the 20% where there is no obvious answer. A yes-man that always emits a confident reply is worse than nothing — the operator would have to re-read everything, so no time is saved. The moat is Bean's ability to know when it is not confident, so the operator can trust the HIGH bucket blindly and spend attention only where it is needed. Every factual claim in a draft must trace to a held source; if it cannot be grounded, Bean does not fabricate — it escalates. This "source-grounded or ask" rule is the acceptance invariant of the whole system.

The learning loop

The triage engine is the throwaway 80%. The moat is that Bean gets better at the operator's voice and judgment with every correction — a closed loop: capture every human action, then feed their past decisions back into the next draft. Shipped 2026-06-25, provider-agnostic.

An approve captures the accepted draft as final_text + the email context in meta; an edit carries original+final so the cosmetic/substantive tagger runs. Those become the (email → good reply) pairs few-shot learns from.

The recategorize signal

A relabel is captured orthogonally — no new action, no schema change.

The draft view has a category dropdown. When the operator relabels the bucket, that is a classification correction, independent of the draft action (they can relabel and approve, edit, or take over). It is recorded as category (their final pick) vs meta.model_category (the model's original) — any row where they differ is the relabel signal. meta is the designed free-dict extension point, so this needs no enum and no schema migration.

Onboarding & operating model

Two reframes (2026-06-25) override the earlier "FDE + native-app + Proton Bridge" framing: Bean is a product (self-serve onboarding that scales past customer #1 without Sameer in the loop), and it never stores a raw mailbox credential. The credential constraint picks the connection model — and is the better product anyway.

Connection model

Forward + domain authentication (the helpdesk pattern) — primary. OAuth — secondary.

The customer forwards their support@ mail to Bean and verifies their domain via DNS (an SPF include + a DKIM key delegated to their domain + a custom Return-Path). Bean reads inbound and sends replies as support@theirbrand.com through its own infra — with zero credentials, and provider-agnostically (Gmail, Outlook, and Proton). This is how Gorgias / Front / Help Scout onboard. OAuth (Gmail/Outlook) is the secondary path: one-click, revocable token, invisible with no DNS — but it can't serve Proton.

Why this dissolves the Proton problem: the blocker was never "Proton has no API" — it was "we were trying to log in as them." Stop logging in. Forward in, send out domain-authenticated. Works on Proton as long as there's a custom domain — customer #1's is hello@sableandwren.example.

Value before friction

The onboarding sequence is ordered so the operator sees Bean work before any DNS.

(1) enter address → (2) import ~20 recent emails → real drafts appear (no DNS, no forward rule, no credentials yet) → (3) Bean bootstraps their voice from their sent replies (this replaces the questionnaire and FDE pre-seeding) → (4) first approve = the success moment → (5) then the one-time forward rule + DNS to go live. Replies then send invisibly as their brand. Full design in roadmap.md § Onboarding.

The two load-bearing invariants

Two things must hold or the system loses its edge: cache stability and calibrated trust.

Invariant 1

Byte-identical cached system prefix

build_system_prefix() runs once per triage and its output is shared as a single cached content block across both model legs. The cache hit requires the bytes to be exactly the same across calls — any whitespace drift, key-order change, or timestamp would bust the cache, double cost, and shift the calibration anchors the model reasons against.

Mechanism: _render_dict renders sorted(d); KnowledgeStore.all() and Config.to_dict() sort their docs; no timestamps or UUIDs in the prefix. KB images ride as separate image blocks, never inside the text prefix — so the prefix stays byte-identical even when screenshots are present.

The learning loop respects this. Few-shot examples are per-email and per-customer, so they ride in the per-email assess_user() message — never the cached prefix. The empty-log path renders the exact pre-few-shot string, so an inbox with no corrections yet is byte-identical to before the loop existed.

Guards: tests/test_config_snapshot.py::test_default_config_prefix_is_byte_identical + tests/test_fewshot.py (asserts examples reach the user message but never the system block, and the empty-log regression). Never weaken them — if they fail, the cache is broken.

Invariant 2

Calibrated confidence routing

The golden set (fixtures.GOLDEN: 8 emails) defines the correct HIGH/LOW/FLAG label per archetype; the calibration test runs live model calls and checks every result against its expected label. HIGH must be sourced — the anti-fabrication gate requires a HIGH result to cite its sources, or it is not allowed into the blind-trust bucket.

mm-0998 is the boundary case: a Returns & Exchanges email with a worn / used item. Its confidence legitimately wavers low ↔ flag run-to-run (~40% flag, ~60% low) because "is worn-item returnability grounded?" is genuinely ambiguous under the policy. It is resolved with also_accepts={Confidence.FLAG} — deterministic suite without forcing a false label. Every other golden stays strict. The waver is surfaced, not suppressed.

The config-as-data spine

The operator's data (categories, templates, knowledge docs, settings) was previously hardcoded in bean/fixtures.py constants. Phase 1 moved it into an injected Config dataclass the routing engine is fed — so swapping in their real data is a file swap, not a code edit. The engine reads whatever Config it receives; the fixtures remain only as the default fallback.

On-disk shape — bean-config.json

{
  "categories": [
    { "name": "Order Status", "description": "Where-is-my-order...",
      "template": "Hi {name}, thanks for reaching out! ...", "alwaysEscalate": false },
    { "name": "Wholesale", "description": "Bulk / B2B...",
      "template": null, "alwaysEscalate": true }
  ],
  "knowledgeDocs": [
    { "title": "returns-policy", "body": "...", "image": "/path/to/screenshot.png" }
  ],
  "settings": { "shopifyStore": "sable-and-wren" }
}

Example vs gitignored

  • bean-config.example.json — committed; the fixtures data as a reference shape.
  • bean-config.json — gitignored; the operator's real (or edited) config, written by the server on every PUT /api/config.

The FLAG rule, as data

  • A category with template: null OR alwaysEscalate: true always routes to FLAG (Category.flags property).
  • This is how Wholesale and Escalation work without a code change.
Never-crash load

load_config() degrades to safe defaults

Missing file → fixtures default + warning. Malformed JSON → fixtures default + warning. Wrong shape → fixtures default + warning. A bad edit degrades to safe defaults rather than taking the loop down — load_config() never raises.

Shipped vs pending

Live now (engine is fully config-driven end-to-end) vs what waits on the operator's real data.

Live now

Through 2026-06-25

  • Config-as-data — engine is config-driven end to end; swapping in the operator's data is a file swap, not a code edit.
  • Server — GET/PUT /api/config + POST /api/preview + POST /api/correction + static web/; persists to data/{customer}/ on the volume.
  • The learning loop — UI captures every action (approve/edit/take-over/snooze + recategorize) to the log; few-shot feeds same-category past replies back into the draft step. Provider-agnostic.
  • The General/IDK gate — low classification-confidence routes to General (no draft, "which bucket is this?"), the cleanest learning signal.
  • Web UI (3-bucket inbox, per-confidence draft view, "Teach Bean" admin), vision wiring, threads, golden calibration (8 cases + also_accepts).

Designed, not built

Next phases

  • Phase 4 — real-data calibration. Swap placeholder categories/templates/docs for the operator's real ones → re-run the golden suite on real emails. Waits on their questionnaire.
  • Mail connection (onboarding). Source/EmlSource ingest (zero auth — also the onboarding import) → then forward+domain-auth: DNS-record generation + verification polling, the domain-authenticated send path, and OAuth as the secondary provider. No mailbox credentials, ever.
  • Voice bootstrap from their sent replies (auto-infer categories/tone/templates). Shopify Admin API (read-only) when deep-links aren't enough. Vector retrieval when the KB outgrows the in-prefix approach.
North star — a self-serve product, not a per-customer setup. A new customer connects their own inbox (forward + domain-auth, no credentials), Bean bootstraps their voice from their sent mail, and the correction log makes it irreplaceable over time. The thin triage → draft → approve wedge, with the learning loop compounding, is what earns the right to widen.
